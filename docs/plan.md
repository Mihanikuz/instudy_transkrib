Сервисный API на стороне instudy проектирует архитектор (ARCH-2, [PR #35](https://github.com/Mihanikuz/instudy/pull/35)) и реализуют задачи BE-14 и следующие по его нарезке. До их слияния мы пишем клиента по черновику `docs/contract.md` и проверяем его на фейковом instudy (`tests/fake_instudy.py`). Боевой запуск (T-9) — только после выкладки сервисного API в instudy.

## Цикл одной задачи

1. Оркестратор переводит задачу в «в работе», агент работает по промту.
2. Агент открывает PR по правилам CLAUDE.md.
3. Ревью: соответствие промту, критерии приёмки — тестами, безопасность (секреты в логах).
4. Человек сливает PR, когда CI зелёный; оркестратор обновляет статус.

## Что проверяется только у человека на GPU-сервере

- `scripts/gpu_smoke.py` — модели грузятся на CUDA и распознают тестовую фразу (T-2);
- `docker compose up` и healthcheck (T-7);
- замеры времени, VRAM и качества на реальных лекциях 1, 3 и 5 часов (T-8);
- боевой прогон с instudy и запуск архива (T-9).
