# Архитектура instudy_transkrib

Oct 22, 2026 · @Mikhail

## Итог

Один Docker-контейнер с GPU на домашнем сервере. Внутри — демон, который в цикле берёт у instudy одну работу, скачивает аудио дня, размечает спикеров pyannote, распознаёт речь GigaAM кусками до 25 секунд и отправляет в instudy `.vtt` и `.txt`. Очередью, приоритетом, правами и хранением транскриптов владеет instudy; у нас нет базы, веб-интерфейса и входящих портов.

| Вопрос | Решение | Почему |
| --- | --- | --- |
| Связь с instudy | Pull по HTTPS, сервисный токен | Сервер за NAT; instudy — единственный хозяин очереди ([001](decisions/001-scope.md)) |
| ASR | GigaAM `v3_e2e_rnnt`, обычный `transcribe` на кусках ≤ 25 с | Пунктуация; `transcribe_longform` не нужен — куски даёт разметка pyannote |
| Диаризация | pyannote community-1, `exclusive_speaker_diarization` | Без перекрытий проще резать и подписывать реплики |
| Параллелизм | Одна работа за раз, один процесс | Одна видеокарта; 5-часовая запись — минуты, а не часы |
| Состояние | Только файлы в `data/`: рабочий каталог работы и `state.json` | Работа одна, очередь у instudy — базе нечего хранить |
| Модели | Офлайн из `models/`, скачиваются один раз | Нет зависимости от Hugging Face в работе |

## Окружение

- Ubuntu 26.04, i7-12700 (20 потоков), 61 ГБ ОЗУ, 256 ГБ свободно на NVMe.
- RTX 5060 Ti 16 ГБ, compute capability 12.0 (Blackwell, sm_120), драйвер 595.99. В контейнере — колёса torch под CUDA 12.8 (поддерживают sm_120; проверено gigascribe на этой же карте с torch 2.8.0+cu128).
- Docker 29, Compose 2.40, NVIDIA Container Toolkit 1.19, runtime `nvidia`.
- Сеть: LAN `192.168.24.37`, выход через NAT. Доступны github.com, huggingface.co, pypi.org, download.pytorch.org.
- На сервере уже есть модели gigascribe (`models/gigaam/v3_e2e_rnnt/`, `models/pyannote/community-1/`) — их можно скопировать вместо повторной загрузки (T-2).

## Компоненты

```
transkrib/
  config.py        настройки из окружения (pydantic-settings)
  log.py           JSON-логи в stdout, фильтр секретов
  types.py         общие модели данных (Segment и др.)
  client.py        клиент сервисного API instudy (httpx): health, next, heartbeat, download, result, fail
  audio.py         ffmpeg: m4a → WAV 16 кГц моно; вырезка кусков; длительность
  diarize.py       интерфейс Diarizer + реализация на pyannote (CUDA)
  asr.py           интерфейс Recognizer + реализация на GigaAM (CUDA)
  segment.py       разметка pyannote → куски ≤ 25 с для ASR; назначение спикеров «Спикер N»
  pipeline.py      одна запись целиком: аудио → диаризация → куски → ASR → сегменты; отмена и прогресс
  render.py        сегменты → .vtt и .txt (контракт, «Формат результата»)
  daemon.py        цикл: next → download → pipeline → result/fail; heartbeat в отдельном потоке; сигналы
  state.py         data/state.json: что делаем сейчас, статистика, пауза
  models_store.py  пути к моделям, проверка, загрузка (разовая, с HF_TOKEN)
  cli.py           status, check, pause, resume, run-file, models-check, models-download, health
```

Интерфейсы `Diarizer` и `Recognizer` — `typing.Protocol`. torch, gigaam и pyannote импортируются только в `load()` реализаций, поэтому тесты и CI работают без них.

## Обработка одной работы

1. **Аренда.** `GET /jobs/next`. Пусто — ждать `POLL_INTERVAL_SEC` (60 с). Пауза (`data/PAUSE` или `cli pause`) — работу не брать.
2. **Heartbeat.** Сразу после аренды стартует поток: каждые 5 минут `POST /heartbeat`. Ответ `409/410` выставляет флаг отмены; конвейер проверяет его между этапами и между кусками ASR.
3. **Скачивание** в `data/work/<job_id>/audio.m4a` с докачкой по `Range` (до 5 попыток). Проверка размера.
4. **Подготовка аудио.** `ffmpeg -i audio.m4a -ac 1 -ar 16000 -c:a pcm_s16le audio.wav` (5 часов ≈ 576 МБ). Длительность из ffprobe сверяется с `audioDurationSec` (расхождение больше 2 % — предупреждение в лог, не ошибка).
5. **Диаризация** всего WAV одним вызовом pyannote на GPU. Берётся `exclusive_speaker_diarization`. Пустая разметка → `fail no_speech`. Модель pyannote выгружается из VRAM.
6. **Нарезка** (`segment.py`, чистая функция, без GPU):
   - соседние отрезки одного спикера с паузой < 0,5 с склеиваются;
   - отрезок длиннее `MAX_SEGMENT_SEC` (22 с) режется в точке минимальной энергии (RMS по окнам 30 мс) внутри окна [15 с; 22 с]; жёсткий потолок — 24 с;
   - отрезки короче 0,3 с отбрасываются;
   - метки pyannote (`SPEAKER_00`…) переименовываются в «Спикер N» по порядку первого появления.
7. **Распознавание.** GigaAM загружается на GPU, куски вырезаются из WAV в память (numpy/torch-тензор, без временных файлов, если API позволяет; иначе — WAV-файлы во временном каталоге) и распознаются по одному. Ошибка одного куска не роняет запись: кусок пропускается с предупреждением; больше 5 % пропущенных — `fail model_error`. CUDA OOM — `torch.cuda.empty_cache()` и повтор куска; повторный OOM — `fail oom`.
8. **Рендер** `.vtt` и `.txt` по контракту. Пустые тексты не пишутся.
9. **Отправка** `POST /result` (multipart). Сетевые ошибки и `5xx` — повтор с задержкой, пока жива аренда. `202`/`409`/`410` — конец работы.
10. **Уборка.** `data/work/<job_id>/` удаляется всегда. Копия результата (`.vtt`, `.txt`, `meta.json`) хранится в `data/results/<job_id>/` `RESULTS_KEEP_DAYS` дней (по умолчанию 14) — для разбора жалоб на качество.

Модели между работами: обе остаются загруженными, если VRAM хватает (по замеру T-8); иначе каждая загружается на свой этап. Режим выбирается настройкой `KEEP_MODELS_LOADED` (по умолчанию `false` до замеров).

## Ошибки и устойчивость

| Ситуация | Поведение |
| --- | --- |
| instudy недоступен | Повтор с экспоненциальной задержкой до 5 минут, без падения процесса |
| `401` от instudy | Токен отозван/неверен: выдача останавливается, критическая запись в лог, проверка раз в 10 минут |
| Аренда отозвана (`409/410` на heartbeat) | Немедленная отмена, уборка, без `fail` |
| Ошибка обработки | `fail` с кодом из контракта, уборка, следующая работа |
| SIGTERM (`docker compose stop`, обновление) | Текущий этап прерывается, `fail shutdown` (`retryable`), уборка, выход ≤ 30 с (`stop_grace_period: 45s`) |
| Падение процесса | Docker перезапускает (`restart: unless-stopped`); незавершённая работа вернётся в очередь по истечении аренды; при старте каталог `data/work/` очищается |
| Мало места на диске | Перед арендой нужно ≥ `MIN_FREE_GB` (по умолчанию 10 ГБ); иначе пауза и запись в лог |

## Конфигурация

Из `.env` (права `600`), только переменные:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `INSTUDY_API_URL` | — | Базовый адрес API instudy, только `https://` |
| `SERVICE_TOKEN` | — | Сервисный токен (выдаёт админ instudy: `python -m app.cli service-add home-gpu`) |
| `POLL_INTERVAL_SEC` | 60 | Опрос пустой очереди |
| `HEARTBEAT_SEC` | 300 | Интервал продления аренды |
| `MAX_AUDIO_BYTES` / `MAX_AUDIO_SEC` | 300 МБ / 21600 | Проверка работы |
| `MAX_SEGMENT_SEC` | 22 | Нарезка под GigaAM |
| `KEEP_MODELS_LOADED` | false | Держать обе модели в VRAM между работами |
| `RESULTS_KEEP_DAYS` | 14 | Хранение копий результатов |
| `MIN_FREE_GB` | 10 | Минимум свободного места для новой работы |
| `MODELS_DIR` / `DATA_DIR` | `/models` / `/data` | Пути в контейнере |
| `HF_TOKEN` | — | Только для разовой загрузки моделей (`models-download`), в работе не нужен |

## Развёртывание

```
/srv/transkrib/            # клон репозитория
  compose.yml
  Dockerfile
  .env                     # chmod 600
  models/                  # веса, монтируются только для чтения (кроме models-download)
    gigaam/v3_e2e_rnnt/
    pyannote/community-1/
  data/                    # владелец uid 10001
    state.json
    PAUSE                  # есть — новые работы не берутся
    work/<job_id>/         # временные файлы текущей работы
    results/<job_id>/      # копии результатов, RESULTS_KEEP_DAYS дней
```

- Образ: `python:3.12-slim-bookworm` (закреплён по digest) + ffmpeg + колёса torch cu128 + pyannote.audio 4.0.x + GigaAM (коммит закреплён), зависимости с хэшами. Связку версий выбирает T-2 по рекомендации GigaAM.
- `compose.yml`: один сервис `transkrib`, `gpus: all`, `restart: unless-stopped`, `user: 10001`, `read_only: true`, `tmpfs: /tmp`, без `ports:`, `stop_grace_period: 45s`, healthcheck — `python -m transkrib.cli health` (свежесть `state.json` < 3 минут).
- Логи — JSON в stdout, ротация средствами Docker (`json-file`, 10 МБ × 5).

## Безопасность

- Токен — только в `.env` и памяти процесса. Фильтр логов маскирует `Bearer …`, `SERVICE_TOKEN`, query-строку `audioUrl` (`sig=`, `exp=`) и любые строки, совпадающие с токеном.
- Наружу ни одного порта; исходящие — только к `INSTUDY_API_URL` (модели офлайн).
- Проверка TLS включена всегда; `http://` в `INSTUDY_API_URL` запрещён на старте.
- Данные instudy недоверенные: пути строятся только из целого `job.id`; размеры и длительности проверяются до скачивания.
- Контейнер без root, ФС только для чтения, `models/` только для чтения.
- Аудио и транскрипты — персональные данные лекций: рабочие файлы удаляются после работы, копии результатов — по сроку, диск сервера не публикуется.

## Производительность (оценка до замеров T-8)

- 5 часов аудио: диаризация ≈ 3–8 мин, ASR ≈ 5–15 мин на RTX 5060 Ti; скачивание 110 МБ — зависит от канала.
- Пиковая VRAM: pyannote ≈ 2–4 ГБ, GigaAM ≈ 1–2 ГБ; обе модели вместе укладываются в 16 ГБ с запасом.
- ОЗУ: WAV 5 часов ≈ 576 МБ в памяти + эмбеддинги pyannote; 61 ГБ хватает.

Главный риск — поведение pyannote community-1 на 5-часовом файле (время кластеризации и память). Если замер T-8 покажет проблему, диаризация переходит на окна по 60 минут с перекрытием 2 минуты и сшивкой спикеров по эмбеддингам — отдельной задачей.
