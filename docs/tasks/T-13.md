# T-13 · Транскрибатор запускается только под работу

```
Прочитай CLAUDE.md, docs/architecture.md, transkrib/daemon.py, transkrib/pipeline.py, transkrib/asr.py, transkrib/diarize.py, transkrib/cli.py, compose.yml. Ты — senior Python-разработчик.

Решение человека (23.10.2026): пока работы нет, транскрибатор на сервере не запущен. Лёгкий демон только опрашивает instudy; как только появилась запись — запускает транскрибатор, по окончании он завершается.

Сейчас: KEEP_MODELS_LOADED=false выгружает модели между работами, но процесс демона держит импортированный torch и CUDA-контекст (видеопамять и гигабайты RAM) всё время, пока жив контейнер.

Сделай (один контейнер, без доступа к Docker-сокету — сокет = root на хосте, не используем):
1. Разделение процессов. Демон (`python -m transkrib`) — супервизор: опрос, аренда, heartbeat, скачивание, отправка результата и fail, state.json, сигналы. Он НЕ импортирует torch, gigaam, pyannote (тест: после полного цикла с фейковым транскрибатором в sys.modules нет torch).
2. Транскрибатор — дочерний процесс на одну работу: `python -m transkrib.runner <каталог работы>`. Вход — только файлы в data/work/<job.id>/ (аудио + job.json без токена и ссылок); выход — transcript.vtt, transcript.txt, meta.json и progress.json (этап, доля) в том же каталоге. Модели грузит сам и выходит; ни токена, ни INSTUDY_API_URL в его окружении нет (env очищается при запуске).
3. Коды выхода → решения демона: 0 — результат; PipelineError — код + reason в result.json (no_speech, audio_unreadable, …) → fail как сейчас; ServerFault (CUDA, модели) и OOM — отдельный код → fail shutdown и предохранитель T-6a без изменений; падение/сигнал без result.json → model_error, считается в предохранителе; зависание — таймаут max(30 мин, 0,5 × длительность записи) → SIGTERM, через 30 с SIGKILL, fail model_error.
4. Отмена: аренда потеряна (410) или SIGTERM демону → SIGTERM ребёнку, ждать до 20 с, затем SIGKILL; fail shutdown как сейчас; рабочий каталог чистится. Ребёнок в своей группе процессов (ffmpeg внутри него тоже убивается).
5. Прогресс: демон читает progress.json ребёнка и пишет в state.json — cli status показывает этап и проценты как сейчас.
6. Проверка моделей при старте и раз в 10 минут при сбое (T-6a) — тоже дочерним процессом `python -m transkrib.runner --check`; демон после неё по-прежнему без torch.
7. KEEP_MODELS_LOADED убрать (или оставить, но игнорировать с warning) — модели живут ровно столько, сколько ребёнок; описать в docs/architecture.md и README. run-file в CLI работает как раньше (в одном процессе).
8. docs/architecture.md: схема процессов, коды выхода, что в покое на GPU ничего нашего нет.

Критерии приёмки (pytest без GPU: ребёнок — фейковый runner через ту же точку входа с подменой моделей переменной окружения тестов):
- в простое и после работы в демоне нет torch (sys.modules), дочерних процессов нет;
- работа проходит через ребёнка: файлы результата те же, что у конвейера в одном процессе (golden);
- коды выхода 0 / PipelineError / ServerFault / OOM / падение / зависание → ожидаемые fail и счётчик предохранителя;
- 410 во время работы и SIGTERM демону → ребёнок завершён ≤ 20 с, fail shutdown, каталог чист;
- окружение ребёнка без SERVICE_TOKEN, INSTUDY_API_URL; job.json без audioUrl (тест на утечки);
- cli status во время работы показывает этап из progress.json.

Человек на GPU-сервере проверяет: в простое `nvidia-smi` без процессов python, `docker stats` — демон < 200 МБ RAM; во время работы ребёнок виден, после — исчезает; скорость работы та же (± 15 с на загрузку моделей).
```
